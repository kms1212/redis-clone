## 0. 시작 전에 바뀐 것

이번 주부터 당번제가 아니라 **각자 포크에서 자기 코드베이스를 키워 가는 방식**으로 바뀌었다.
그래서 S02는 upstream main(kdh의 std 스레드 구현)이 아니라 **내 S01(tokio + `BufReader`) 위에서** 시작했다.

- 포크 `kms1212/redis-clone`에 `kms1212` 브랜치를 만들어 기본 브랜치로 설정
- 내 S01 커밋 2개를 cherry-pick (충돌은 `src/main.rs`뿐, 내 버전으로 해결)
- 세션별 브랜치 대신 커밋 메시지에 세션을 적는 규칙: `<타입>(sNN): <설명>`

가져와 보니 main의 `01-ping.txt` 10케이스 중 **4개가 실패**했다(`PING a b`, `garbage` 등).
내 S01은 커맨드 이름을 4바이트(`PING`)까지만 읽고 나머지는 연결을 끊었기 때문이다.
S01 때는 케이스가 3개뿐이라 드러나지 않았다 → `fix(s01)`로 먼저 고침.

## 1. 무엇을 만들었나

- `ECHO <msg>`, 인자 개수 오류 문구
- 파이프라이닝: 붙여 보낸 명령마다 응답, **뒤 명령이 덜 와도 완결된 앞 명령은 먼저 응답**
- 프로토콜 에러: `invalid multibulk length` / `invalid bulk length` / `expected '$', got 'x'`를 보내고 연결 종료
- 스펙: [ECHO](https://redis.io/docs/latest/commands/echo/), [RESP](https://redis.io/docs/latest/develop/reference/protocol-spec/)

**에러 문구의 출처는 스펙이 아니라 실측이다.** RESP 스펙에는 `Protocol error: ...` 문구가 나오지 않는다.
진짜 Redis(8.10.2)에 깨진 입력 29종을 직접 보내 응답 바이트와 연결 종료 여부를 맞췄다.

### 2-B. AI가 제안한 것 (내가 골라서 반영)

| 갈림길 | 고른 것 | 이유 | 버린 선택지와 그 이유 |
| --- | --- | --- | --- |
| 범위: 프로토콜 에러 문구 | **맞춤** (단위 테스트로 검증) | 에러 타입이 이번 토론 주제인데, 그 타입이 무엇을 담는지 보여 주는 게 이 문구들 | **안 맞춤**: difftest(redis-cli)로는 검증 불가라 범위 밖이라고 볼 수도 있음. 그러면 에러 enum이 `InvalidRequest` 하나로 끝나 토론할 게 없어짐 |
| 범위: 인라인 명령 | **안 함** | 파서를 하나 더 만드는 일이고 실무에서 안 씀 | — |
| 버퍼 / 읽기 구조 | **S01의 `BufReader` 스트리밍 유지** + 리더를 제네릭(`R: AsyncBufRead`)으로 | 쪼개진 입력은 `read_exact`가 알아서 기다림. 제네릭이라 테스트에서 `&[u8]`·`tokio::io::duplex`를 넘김 | **`Vec` 누적 + 순수 파서**(kdh 방식): S01 구조를 갈아엎어야 하고, 덜 온 명령을 매번 처음부터 다시 파싱(큰 값이면 O(n²)) |
| 인자 `Vec` | **이름을 먼저 읽고 용량을 미리 잡음** (상한 16) | 측정으로 −10.6% (2-3) | `remove(0)`으로 이름 떼기 |
| 깔끔함 정리 | 에러 문구를 응답·로그가 한 곳에서, `wrong_args_reply` 공통 함수, 한도 두 개를 `Limits`로 | 같은 문구·인자가 여러 곳에 흩어져 있었음 | 그대로 두기 |

```
src/
  main.rs          Config, accept 루프
  connection.rs    읽기 → parse → execute → encode → 쓰기, 프로토콜 에러면 응답 후 종료
  resp.rs          읽기만: read_array_len, read_bulk, parse_integer, Limits
  reply.rs         쓰기만: Reply, encode
  error.rs         Error, ProtocolError
  command/         mod.rs(분기, unknown, wrong args), ping.rs, echo.rs
```

### 2-1. 진짜 Redis에 맞춘 세부 동작 (실측으로 알게 된 것)

- 숫자는 `string2ll`처럼 엄격하다: `+1`, `05`, `-0`, 공백 모두 거부. Rust의 `parse::<i64>()`는 `+5`, `05`를 받아 줘서 그대로 쓰면 틀린다
- 헤더는 `\r`까지 읽고 **다음 1바이트는 검사하지 않는다**. 그래서 `*1\n`은 `invalid multibulk length`
- 0 이하 배열 길이(`*-1`, `*0`)는 **무시하고 연결 유지**, `i32::MAX` 초과는 에러
- 에러 문구 안의 `\r`, `\n`은 공백으로 바뀌고, `\xff` 같은 바이트는 그대로 나간다
- arity가 틀렸어도 **프레임 끝까지 읽은 뒤** 응답한다: `*3 ECHO a +x` → arity 에러가 아니라 프로토콜 에러

### 2-2. 측정: 긴 bulk가 MTU 단위로 쪼개져 올 때

1MB 요청을 쪼개는 크기를 바꿔 가며 진짜 Redis와 비교 (release, 최소값).

| 쪼갠 크기 | 조각 수 | 진짜 Redis | 우리 |
| --- | --- | --- | --- |
| 안 쪼갬 | 1 | 465µs | 389µs |
| 16KB | 61 | 557µs | 375µs |
| 1460B | 684 | 1236µs | 1843µs |

- 바이트에 비례하는 비용은 우리가 더 싸다 (`BufReader`가 큰 읽기는 내부 버퍼를 거치지 않고 목적지에 바로 씀)
- 조각마다 **약 0.8µs**가 일정하게 더 든다 → 파서가 아니라 런타임이 조각마다 깨어나는 비용. 앱 코드로는 못 줄임
- kdh 방식(덜 오면 처음부터 다시 파싱)이었다면 여기서 O(n²)가 됐을 것

### 2-3. 측정 방법을 바꾸자 결론이 바뀌었다

처음엔 `redis-benchmark`의 처리량(req/s)으로 비교했는데 차이가 측정 편차에 묻혔다. 원인 두 가지:

1. `-c 1`에서는 서버 CPU 70%, 클라이언트 42% → **왕복 지연**을 재고 있었음
2. `--threads`를 켜면 경과 시간을 **0.25초 단위**로 재서, 값이 다섯 가지로만 나옴 (해상도 ~8%)

그래서 **서버 CPU 시간(user+sys) ÷ 명령 수**로 바꿨다 ([`scripts/cpubench.sh`](../../scripts/cpubench.sh)).
300만 건 × 6라운드, 비교 대상을 라운드마다 번갈아 실행해 짝지은 차이를 본다.

| | `ECHO hello` | `ECHO` + 인자 12개 |
| --- | --- | --- |
| 기준선 | 932ns | 1920ns |
| 이름 먼저 읽기 + 인자 `Vec` 용량 상한 16 | **840ns (−10.6%, 6/6)** | **1748ns (−7.1%, 6/6)** |
| pull 실험 | 815ns (−12.8%, 6/6) | 1893ns (−0.4%, 3/6) |

→ "이름 먼저 + 용량 상한"을 채택 (`perf(s02)`). 코드도 `remove(0)`과 그 설명이 사라져 더 깔끔해졌다.

### 2-4. pull 구조 실험과 폐기 ([코드](https://github.com/kms1212/redis-clone/commit/12eb625))

"프레임을 다 읽어 재배치한 뒤 넘기는 것보다, 커맨드가 직접 꺼내 쓰는 게 낫지 않을까"를 실험했다.

- 동작: 테스트·difftest·프로토콜 에러 비교 모두 통과
- 속도: 인자 1개에선 가장 빠르지만 인자가 많으면 이득이 사라짐 (위 표). 2단계 구조 안에서 용량만 잡아도 비슷한 이득
- **폐기 이유는 복잡도**:
  - 모든 커맨드 `parse`가 `async` + 중첩 `Result<Result<Command, Reply>, Error>`
  - arity 에러 때 남은 인자를 읽어 버리지 않으면 **스트림이 어긋나는데, 컴파일러가 못 잡는다**. 에러 enum·커맨드 enum을 고른 기준("빠뜨리면 컴파일러가 잡는다")과 정반대
  - Redis와 바이트를 맞추려면 어차피 프레임 끝까지 읽어야 해서, pull의 핵심 장점(필요한 만큼만 읽기)을 못 씀

**나중에 이 선택들을 뒤집어야 하는 조건:**

- 커맨드 enum → S10 이후 커맨드별 메타데이터(arity, 플래그, `COMMAND INFO`)가 필요해지면 테이블/trait 검토
- 2단계 → 인자를 다 받기 전에 판단해야 하는 기능(미인증 클라이언트 크기 제한, 큰 값 스트리밍)이 생기면. 그때도 `resp`에 "헤더만 먼저 보는" 훅을 다는 게 범위가 작음
- 용량 상한 16 → 인자 수백 개짜리(`MSET` 등)가 흔해지면 `cpubench.sh`로 다시 측정
- `Reply` → 정수·Null·배열은 쓰는 세션(S03, S06)에서 variant 추가

## 4. 내가 추가한 테스트 케이스

```
ECHO "Hello, world!"
ECHO hello
ECHO Hello, world!
ECHO 헬로월드
ECHO "헬로월드"

EcHo hello
ECHO

ECHO 'hello, world!'
```

- **왜 이 케이스를 넣었나:** 기본 성공, 대소문자 무시, UTF-8 바이트 길이(`$12`), 인자 0개·2개 에러
- **넣었다가 깨진 것:** **difftest는 따옴표를 처리하지 않는다.** `ECHO "Hello, world!"`는 인자 두 개(`"Hello,`, `world!"`)로 나가서 기대값이 wrong arguments 에러가 된다. 처음 9줄 중 6줄이 같은 에러만 테스트하고 있었다
- difftest로 못 보내는 것은 단위 테스트로: 빈 문자열(`ECHO ""`), 파이프라이닝, 프로토콜 에러

## 5. 막혔던 곳

- 측정: 처리량으로는 10% 차이가 안 보였다 → 2-3
- 테스트: 응답이 안 오는 버그가 생기면 테스트가 실패하지 않고 **영원히 멈춤** → `tokio::time::timeout` (tokio `time` feature를 dev-dependency로만 켬)
- **에러 응답 안의 `\r\n` 버그**: unknown command 문구는 클라이언트가 보낸 인자를 그대로 넣는데, 인자에 `\r\n`이 있으면 응답이 중간에 끝난 것처럼 읽혀 이후 응답이 전부 어긋났다. 응답 인코딩을 `Reply` 한 곳에 모으다가 발견 → 모든 에러 응답에 공백 치환 적용

## 6. 새로 배운 Rust 개념

- **데이터를 담은 enum + 중첩 패턴**: `Err(Error::Protocol(e))`, 슬라이스 패턴 `[b'1'..=b'9', rest @ ..]`
- **제네릭 + trait bound**: `S: AsyncRead + AsyncWrite + Unpin`. 테스트에서 `&[u8]`, `DuplexStream`을 소켓 대신 넘김
- **`self` 소비와 move**: `execute(self)`, `into_iter()`로 인자를 복사 없이 `Reply::Bulk`까지 넘김 (`.clone()` 0개)

## 7. 알려진 차이 (테스트 케이스에 없어서 통과)

| 입력 | 진짜 Redis | 우리 |
| --- | --- | --- |
| unknown command의 긴 인자 | 인자를 128자에서 자름 | 자르지 않음 |
| `$4\r\nPINGXX\r\n` (bulk 뒤 `\r\n` 아님) | 검사 없이 받아 줌 | 문구 없이 연결 종료 |
| 헤더 줄이 64바이트 초과 | 64KB까지 받고, 넘으면 `too big ... string` | 문구 없이 연결 종료 (학습용 한도) |
| bulk 크기 한도 | 512MB | 1MB (학습용 한도, 넘으면 `invalid bulk length`) |
| 인라인 명령 (`nc`로 친 생 텍스트) | 지원 | 연결 종료 |
| 파이프라이닝 응답 쓰기 | 출력 버퍼에 모아 한 번에 | 명령마다 `write` (바이트는 같음, 시스템 콜 수가 다름) |
