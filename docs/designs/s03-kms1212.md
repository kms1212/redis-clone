# S03 SET / GET / DEL / EXISTS — kms1212

- 구현 브랜치: [`kms1212`](https://github.com/kms1212/redis-clone/tree/kms1212) (`git log --oneline --grep '(s03)'`)
- 걸린 시간: 약 30분 (10/10 00:18 ~ 00:49. 준비·구현·측정 약 25분, 설계 문서 약 5분)

## 1. 무엇을 만들었나

- `SET key value` → `+OK`, `GET key` → 값 또는 Null(`$-1`), `DEL key [key …]` → 지운 개수, `EXISTS key [key …]` → 있는 키 개수
- 모든 연결이 같은 저장소를 공유 (한 연결에서 SET, 다른 연결에서 GET)
- `Reply`에 `Integer`와 `Null` 추가 (S02에서 "쓰는 세션에서 추가"로 미뤄 둔 것)
- 스펙: [SET](https://redis.io/docs/latest/commands/set/), [GET](https://redis.io/docs/latest/commands/get/), [DEL](https://redis.io/docs/latest/commands/del/), [EXISTS](https://redis.io/docs/latest/commands/exists/)

진짜 Redis(8.10.2)를 먼저 찔러 보고 알게 된 것:

| 입력 | 응답 | 의미 |
| --- | --- | --- |
| `DEL a b c a` | `:2` | 같은 키를 두 번 적어도 **한 번만** 셈 (두 번째 `a`는 이미 지워짐) |
| `EXISTS a a nokey` | `:2` | 반대로 **중복을 따로따로** 셈 |
| `SET k v foo` | `ERR syntax error` | 모르는 옵션 |
| `SET k v EX 10` | `OK` | 옵션은 S04 범위 |

### 2-B. AI가 제안한 것 (내가 골라서 반영)

| 갈림길 | 고른 것 | 이유 | 버린 선택지와 그 이유 |
| --- | --- | --- | --- |
| **동시성 모델** | **`Arc<std::sync::Mutex<Store>>`**, 락은 명령 하나 동안만, 커맨드는 `&mut Store`만 받음 | 가장 짧고, 나중에 락 방식을 바꿔도 커맨드 코드는 그대로. `Arc<Mutex>`는 `Send + Sync`라 멀티스레드 런타임으로 바꿔도 코드 수정 없이 동작 | **샤딩**: 멀티스레드에서 다른 키끼리 진짜 병렬이 되지만, `DEL a b`처럼 여러 키면 락을 순서대로 여러 개 잡아야 하고 S09 `MULTI`/`EXEC` 원자성이 가장 어려움. **actor + 채널**: 진짜 Redis 6+ 구조(I/O 여러 스레드, 실행 하나)와 같고 S07에 유리하지만, 명령마다 스레드를 건너는 비용과 코드 양. **`Rc<RefCell>`**: `Send`가 아니라 멀티스레드 불가 |
| std `Mutex` vs `tokio::sync::Mutex` | **std** | `execute`가 동기라 락을 잡은 채 `.await`할 일이 없음. 이 경우 std가 가볍고, tokio 문서도 권장 | tokio `Mutex`: `.await`를 걸치는 락이 필요할 때 쓰는 것 |
| 런타임 | **`current_thread` 유지** (멀티스레드 전환은 따로) | A안은 바꿔도 그대로 동작하니, 전환은 측정을 포함한 별도 작업으로 떼는 게 범위가 깔끔 | 지금 전환: S03 범위가 "멀티스레드 성능"까지 커짐 |
| 락 poisoning | **`unwrap_or_else(PoisonError::into_inner)`로 복구** | 프로덕션 코드에 패닉 경로가 없고, HashMap 연산 하나가 중간에 끊겨도 맵이 깨지지 않음 | 연결 끊기: 그 뒤 모든 연결이 끊겨 서버가 사실상 죽음. `parking_lot`: poisoning이 없지만 새 의존성 |
| 키/값 타입 | **`HashMap<Vec<u8>, Vec<u8>>`** | Redis 문자열은 바이너리 안전. `SET`의 값이 소켓에서 읽은 `Vec` 그대로 **move로** 저장소에 들어감 | `String`: UTF-8이 아닌 값을 못 담음. `BTreeMap`: 순서는 S10 `SCAN`의 토론 주제 |
| `SET` 추가 인자 | **일괄 `ERR syntax error`** | 옵션은 S04 범위 | 옵션 일부 구현: 범위 초과 |

### 2-1. 규칙을 사람이 아니라 컴파일러가 지키게

- **"락을 잡은 채 `.await` 금지"**: 일부러 어겨 보니 `MutexGuard ... is not Send ... used across an await` **컴파일 에러**. std `MutexGuard`가 `Send`가 아니고 `tokio::spawn`이 `Send`를 요구하기 때문. PR 체크리스트 항목을 타입이 지킴
- **커맨드 추가 시 빠뜨리기**: 매크로 목록에 넣고 trait 구현을 빠뜨리면 `CommandSpec is not implemented` 컴파일 에러. 가짜 커맨드를 추가해 보며 "기존 파일에서 고칠 곳은 목록 한 줄뿐"인 것도 확인
- **표 항목 실수**: 소문자나 16바이트 초과 이름을 표에 넣으면 컴파일은 되지만 영원히 매칭 안 됨 → 테스트로 막음

## 4. 내가 추가한 테스트 케이스

```
# 없는 키는 Null, SET 하면 다른 커넥션에서도 보임
GET name
SET name hello
GET name

# 덮어쓰기
SET name world
GET name

# 커맨드 이름 대소문자, UTF-8 키와 값
sEt 한글키 헬로월드
GeT 한글키

# DEL은 지운 개수를 셈. 같은 키를 두 번 적어도 한 번만 셈
SET a 1
SET b 2
DEL a b nokey a
GET a
DEL a

# EXISTS는 반대로 중복을 따로따로 셈
SET c 3
EXISTS c
EXISTS c c nokey
EXISTS nokey

# 숫자처럼 보이는 값도 그대로 문자열
SET n 10
GET n

# 인자 개수 에러
SET
SET k
GET
GET a b
DEL
EXISTS

# SET 옵션은 S04 범위. 모르는 옵션은 syntax error
SET k v foo
```

- **왜 이 케이스를 넣었나:**
  - difftest는 **줄마다 `redis-cli`를 새로 띄워서**, `SET` 다음 줄의 `GET`이 곧 로드맵 완료 기준("다른 커넥션에서 SET한 값이 보임")의 검증
  - `DEL a b nokey a` / `EXISTS c c nokey`: 중복 키를 세는 방식이 반대라, 한쪽 방식으로 둘 다 짜면 깨짐
- **넣었다가 깨진 것 / 한계:** **redis-cli는 응답을 텍스트로 바꿔 출력해서 정수 `:2`와 bulk `"2"`, Null과 빈 문자열이 똑같이 보인다.** DEL이 문자열 "2"를 돌려줘도 difftest는 통과한다. 그래서 응답 타입은 단위 테스트(`Reply::Integer(2)`, `Reply::Null`)와 진짜 Redis와의 바이트 비교(`nc`)로 확인

## 5. 막혔던 곳

- 위 redis-cli의 타입 구분 문제 → 바이트 비교 스크립트로 명령 20개(빈 문자열, `\xff\x00\r\n` 같은 바이너리 값 포함)를 진짜 Redis와 비교해 일치
- `pub(super)` 커맨드 struct를 `pub(crate)` enum에 넣자 "비공개 타입이 공개 인터페이스에 나온다" 에러 → struct는 `pub(crate)`, 필드는 비공개로

## 6. 새로 배운 Rust 개념

- **`Arc` + `Mutex` + `MutexGuard`(RAII)**: 여러 연결이 저장소를 공동 소유하고, guard가 스코프를 벗어나면 락이 풀림. guard가 `!Send`라 `.await`를 넘어 들 수 없음
- **`macro_rules!`**: `$(...)+` 반복으로 `mod`, `enum`, `impl` 같은 아이템 자체를 생성
- **함수 포인터와 `LazyLock`**: `fn(..) -> ..`를 값으로 표에 넣고, 전역 표를 처음 접근할 때 한 번만 초기화
